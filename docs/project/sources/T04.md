# T04: vizita și manoperele efectuate

## Rezultat

Medicul deschide o programare, începe vizita și adaugă una sau mai multe manopere din catalogul T03. Fiecare poate fi pornită, pusă pe pauză, reluată și finalizată. Programarea se închide separat după discuția cu pacientul. UI, API și persistența trebuie să funcționeze împreună.

## Contract și decizii de implementare propuse

Consemnează numele și API-urile exacte înainte de cod; cele de mai jos definesc comportamentul, nu impun nume care ar duplica modele existente.

- Folosește Appointment drept contextul vizitei dacă nu există un motiv concret pentru entitate separată; nu dubla pacientul, clinica sau stările fără nevoie.
- Manopera efectuată are UUID, clinică, pacient, programare, medic executant, referință catalog și snapshot pentru cod/denumire, preț, monedă și durată estimată. Adaugă localizare opțională: dinte FDI adult și suprafețe validate. Pentru servicii fără dinte, localizarea poate lipsi. Nu construi odontograma T06 și nu inventa reguli T03 de localizare care nu există încă.
- Stări propuse: pending, running, paused, completed, cancelled. Documentează și testează tranzițiile permise. Nu porni timpul la simpla adăugare.
- Start, pause, resume și complete folosesc timpul serverului și segmente persistate. Durata efectivă este suma segmentelor active; pauzele nu se includ. Reload-ul, schimbarea tabului și restartul serverului nu pierd timpul. Un timer vizual nu este sursa de adevăr.
- Păstrează istoricul tranzițiilor. Repetarea unei cereri nu dublează segmentele sau închiderile; documentează dacă răspunzi idempotent sau cu 409 la tranziții deja consumate.
- Protejează tranzacțional regula unui singur timer running per medic între toate programările. Testează două starturi concurente și start/resume concurent pe PostgreSQL real, cu cel mult un succes activ. SQLite nu dovedește regula de concurență.
- Propunere de închidere: nu completa vizita cât timp există manopere running sau paused; enumeră manoperele care necesită rezolvare. Manoperele pending trebuie finalizate sau anulate explicit. Nu opri și nu completa automat manopere la închiderea programării.
- Nu permite mutații de execuție în vizite completed/cancelled/no_show. Păstrează posibilitatea de corecție istorică autorizată, fără redeschidere tacită.
- Durata introdusă retrospectiv are sursa manuală, motiv, autor și timestamp; nu fabrica segmente măsurate. Definește cum sunt reprezentate corecțiile înainte de cod.
- Copiază prețul la crearea manoperei; folosește Decimal în backend și serializare monetară consecventă. O schimbare ulterioară în catalog nu schimbă manopera. Modificările autorizate ale tarifului manoperei se auditează cu valori vechi/noi și motiv. Fără contabilitate sau plăți.

## Roluri propuse pentru acest modul

Reutilizează autentificarea existentă. Manager/administrator și medic pot gestiona manopere; medicul obișnuit execută pentru identitatea sa, fără impersonare prin doctor_id arbitrar. Asistentul și recepția nu pot porni/opri cronometre sau modifica înregistrări clinice. Pentru vizualizare, documentează o matrice explicită de câmpuri și roluri; nu extinde accesul la note clinice din comoditate. Deciziile noi sunt propuneri pentru review, nu politici istorice confirmate.

## UI și API

- Intrare din detaliile programării către vizită; acțiune de start compatibilă cu tranzițiile Appointment existente.
- Listă de manopere, selecție din catalog activ, localizare și preț; controale start/pause/resume/complete și sursa duratei afișate explicit.
- Închiderea separată a vizitei, cu mesaje pentru manopere nerezolvate.
- Loading, empty, erori de validare, 403, 409 și operații pending vizibile. Schimbarea pacientului/programării nu transferă starea formularelor.
- API-uri tipate pentru listare/creare/tranziții/durată manuală/corecții și istoric; validări, ownership și audit server-side, nu doar UI.

## Dovezi cerute

- Ciclu complet start → pause → resume → complete; durată exactă cu ceas controlat și după reload.
- Două manopere într-o vizită; finalizarea uneia nu închide programarea.
- Timer unic concurent per medic și independență între doi medici.
- Tranziții invalide, retry, intervale/durate invalide și vizite închise.
- Schimbarea catalogului nu modifică snapshotul; corecții cu motiv și istoric.
- Cross-clinic pentru toate referințele și operațiile, plus matrice de roluri.
- Migrare de la baseline populat la T04 cu verificarea datelor existente, fără drop/recreate.
- Frontend și API folosesc contracte sincronizate, build și teste trecute. Browser real unde mediul permite; altfel raport exact al lipsei.

Nu începe T05 până când acest contract este stabil și verificările proprii disponibile trec. Predă separat raportul T04 și deciziile de review înainte să construiești branch-ul derivat.
