# T08 Treatment plans — API contract v1

Module: backend `app/treatment_plans/`, frontend `src/treatment-plans/`, entry point
"Planuri de tratament" in the patient clinical record. Migration
`t08_add_treatment_plans` (down revision `t06_add_persisted_odontogram`), additive only.

All endpoints are under `/api/treatment-plans`, require a bearer token and the role
`doctor`, `clinic_manager` or `administrator`. Reception and assistants get `403`.
Clinic identity always comes from the authenticated user; foreign patients, plans,
items, catalog entries, appointments and performed procedures answer `404`.
JSON is snake_case; money is a decimal **string** with two decimals (numbers are
refused with `422`). Timestamps are ISO-8601.

Planning never creates performed procedures, prices to collect or timer segments.
Execution stays in T04/T07; T08 only reads T04/T02 rows and links to them.

## Plan status matrix

| From | To | Trigger |
|---|---|---|
| `draft` | `accepted` | `POST /{id}/accept` (needs ≥1 active item) |
| `draft`/`accepted`/`in_progress` | `cancelled` | `POST /{id}/cancel` with reason |
| `accepted` | `draft` | any content/estimate edit (version bump) |
| `accepted` | `in_progress` | first performed-procedure link |
| `in_progress` | `in_progress` | content edit bumps version, `needs_acceptance=true` |
| `accepted`/`in_progress` | `completed` | `POST /{id}/complete` |

`completed` and `cancelled` are terminal and read-only. Cancelling a plan never
cancels appointments or performed procedures and keeps all links and history.

Completion requires: current version accepted, every item either `done` or
explicitly `cancelled`, and at least one `done` item (otherwise cancel the plan).

## Versions and acceptance

- `version` starts at 1. The first content edit after an acceptance increments it once;
  further edits stay in the same unaccepted version.
- Content edits: plan title/notes, stage add/edit/move/delete, item add/edit/delete.
  Item cancellation and links are progress actions and do not change the version.
- `POST /{id}/accept {note, expected_version?}` records an **internal staff record**
  (actor, time, note) with a frozen snapshot of stages, items and totals for that
  version. It is not an electronic signature and not proof of patient consent.
  `409` when the version is already accepted or `expected_version` is stale.
- `acceptances[]` keeps every accepted version; `is_current` marks the one equal to
  the current `version`. `needs_acceptance` is true while the current version is unaccepted.

## Item progress (derived on read)

| `progress` | Meaning |
|---|---|
| `planned` | no links |
| `scheduled` | appointment linked, no performed procedure |
| `in_progress` | linked performed procedure is `pending`/`running`/`paused` |
| `done` | linked performed procedure is `completed` |
| `attention` | linked performed procedure was `cancelled` — not done; unlink or relink |
| `cancelled` | item cancelled explicitly with reason |

Stage and plan `progress`: `{total, done, cancelled, in_progress, scheduled, planned,
attention, remaining, percent}`; `percent = done / (total - cancelled)`.

## Estimates

Each item snapshots `procedure_code`, `procedure_name`, `currency`,
`estimated_price` (default catalog `base_price`, overridable) and
`estimated_duration_minutes` (default catalog duration). Catalog edits or
deactivation never change existing items; inactive services cannot be added (`409`).
`totals[]` is computed server-side **per currency** (no cross-currency sum):
`estimated_total`, `completed_estimate`, `remaining_estimate`, `estimated_minutes`;
cancelled items are excluded.

## Location

`tooth_fdi`: optional FDI permanent tooth (`11`–`48`, same validator as T04).
`tooth_surface`: optional comma-separated T04 surface vocabulary, normalised sorted;
surfaces require a tooth.

## Links

- `PUT /items/{item_id}/appointment {appointment_id|null}` — appointment of the same
  clinic and patient, not `cancelled`/`no_show`. Allowed in draft/accepted/in_progress.
- `PUT /items/{item_id}/performed-procedure {performed_procedure_id}` — only for
  accepted/in_progress plans; the performed procedure must belong to the same patient,
  use the same catalog service, the same tooth and the same surface set, and not be
  cancelled (`404`/`422`/`409`). Repeating the same link is a no-op `200`.
- A performed procedure fulfils at most one item across all plans: unique index
  `uq_treatment_plan_item_performed`; a concurrent loser gets `409`.
- `DELETE /items/{item_id}/performed-procedure {reason}` unlinks with history.
- Linked actor/time are stored on the item and every change is in `history[]`
  (`treatment_plan_events`) plus `audit_events`.

## Endpoints

| Method | Path | Notes |
|---|---|---|
| GET | `/patients/{patient_id}` | summaries (status, version, totals, progress) |
| POST | `/patients/{patient_id}` | create `{title, notes?, stages:[{title, notes?, items:[item]}]}`; optional `Idempotency-Key` UUID |
| GET | `/patients/{patient_id}/link-candidates` | patient's appointments and non-cancelled performed procedures with `linked_item_id` |
| GET | `/{plan_id}` | full plan: stages, items, totals, progress, acceptances, history |
| PATCH | `/{plan_id}` | `{title?, notes?}` |
| POST | `/{plan_id}/stages` | `{title, notes?, items?}` |
| PATCH | `/{plan_id}/stages/{stage_id}` | `{title?, notes?, move?: up|down}` |
| DELETE | `/{plan_id}/stages/{stage_id}` | empty stages only |
| POST | `/{plan_id}/stages/{stage_id}/items` | item; optional `Idempotency-Key` |
| PATCH | `/items/{item_id}` | `{tooth_fdi?, tooth_surface?, priority?, estimated_price?, estimated_duration_minutes?, notes?, stage_id?}`; location locked while a performed procedure is linked |
| DELETE | `/items/{item_id}` | unlinked items only |
| POST | `/items/{item_id}/cancel` | `{reason}`; not while a performed procedure is linked |
| PUT/DELETE | `/items/{item_id}/appointment`, `/items/{item_id}/performed-procedure` | see Links |
| POST | `/{plan_id}/accept`, `/{plan_id}/complete`, `/{plan_id}/cancel` | see matrix |

Item input: `{procedure_catalog_id, tooth_fdi?, tooth_surface?, priority?: urgent|high|normal|low,
estimated_price?: "0.00", estimated_duration_minutes?, notes?}`.
Every mutation returns the full plan.

## Concurrency

Every mutation locks the plan row (`SELECT … FOR UPDATE`, order plan → item) and
never locks T04 rows. The cross-plan single-fulfilment invariant is enforced by the
unique index and verified in `tests/test_postgres_treatment_plans.py`.

## Out of scope

Billing (T13), patient portal, PDF, e-signature, notifications, automatic migration of
existing `treatment_plan` clinical notes, creating/timing procedures from the plan.
