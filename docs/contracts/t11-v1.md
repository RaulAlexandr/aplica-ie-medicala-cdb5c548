# T11 v1 — documente și imagini protejate în dosarul pacientului

Status: pilot local, date fictive. **Nu este validat pentru utilizare clinică reală.** Fără DICOM, integrare aparate, OCR/AI, portal pacient, semnare, editare imagini sau interpretare diagnostică.

## Roluri

| Rol | Acces T11 |
| --- | --- |
| `doctor`, `clinic_manager`, `administrator` | listare, încărcare, vizualizare/descărcare conținut, arhivare |
| `reception`, `assistant` | **403** pe toate rutele T11, inclusiv conținutul direct |
| neautentificat | 401 |
| altă clinică | 404 (pacient, document, conținut, arhivare), fără a confirma existența |

Permisiunile altor module nu se schimbă.

## Rute (prefix `/api/documents`)

| Metodă și rută | Descriere |
| --- | --- |
| `GET /limits` | formate, limite, categorii, `antivirus_scan: false` (afișate în UI) |
| `GET /patients/{patient_id}?include_archived=false` | metadate, cele mai noi primele; arhivatele doar la cerere |
| `GET /patients/{patient_id}/visit-options` | vizitele (appointments) pacientului, numai citire, pentru asociere |
| `POST /patients/{patient_id}` | încărcare (vezi mai jos), 201 |
| `GET /{document_id}` | metadatele unui document |
| `GET /{document_id}/content[?download=true]` | conținutul, după autorizare |
| `POST /{document_id}/archive` `{"reason": "..."}` | retragere cu motiv; păstrează metadate și fișier; 409 dacă e deja arhivat |

### Încărcare

Corp brut `application/octet-stream` (nu multipart), astfel încât limita se aplică **în timpul citirii fluxului**.

- Query: `category` (`photo` | `radiograph` | `document` | `other`, obligatoriu), `appointment_id`, `tooth_fdi` (11–18, 21–28, 31–38, 41–48), `clinical_date` (`YYYY-MM-DD`, nu în viitor).
- Headere: `X-File-Name` (UTF-8 percent-encoded; numai metadată de afișare), `X-Document-Description` (opțional, ≤500), `Idempotency-Key` (UUID, opțional).
- Validare server-side: pacientul aparține clinicii; vizita aparține **acestui pacient** (altfel 422); dintele este FDI valid. O pre-verificare fără lock se face înainte de citirea corpului (conexiunea DB este eliberată cât timp clientul transmite fișierul). Verificarea definitivă se face după staging și inspecție, cu **lock pe rândul programării** (`SELECT … FOR UPDATE`), în aceeași tranzacție cu inserarea și până la commit.
- Retry cu același `Idempotency-Key` și același conținut (SHA-256) întoarce documentul existent; alt conținut sau alt pacient → 409.

### Răspunsul de conținut

`Content-Type` = tipul detectat la încărcare; `X-Content-Type-Options: nosniff`; `Cache-Control: private, no-store`; `Content-Security-Policy: default-src 'none'; sandbox`; `Cross-Origin-Resource-Policy: same-site`; `Referrer-Policy: no-referrer`. Imaginile sunt `inline`; PDF este întotdeauna `attachment` (aplicația nu randează PDF). `Content-Disposition` are fallback ASCII și `filename*` UTF-8. Fiecare acces creează un `AuditEvent` (`viewed`/`downloaded`). UI-ul obține conținutul cu header `Authorization` ca blob; nu există token, link semnat sau URL public permanent.

## Formate și limite

| Setare (env) | Implicit |
| --- | --- |
| `DOCUMENT_STORAGE_DIR` | nesetat → T11 răspunde 503 „Document storage is not configured” |
| `DOCUMENT_MAX_BYTES` | 20 MiB / fișier |
| `DOCUMENT_MAX_IMAGE_SIDE` | 12000 px |
| `DOCUMENT_MAX_IMAGE_PIXELS` | 50 000 000 |

- Tipul se detectează din semnătura octeților (PNG, JPEG, PDF); extensia trebuie să corespundă conținutului; MIME-ul declarat de client este ignorat.
- Imaginile sunt validate cu **Pillow** (dependență `pillow>=11,<13`, numai decodare, fără editare): formatul deschis trebuie să fie cel al semnăturii; dimensiunile din antet sunt comparate cu limitele **înainte** de decodare (413); apoi `verify()` (structură, CRC PNG) și decodare completă (`load()`, `LOAD_TRUNCATED_IMAGES=False`), executate în afara event loop-ului. Orice eșec de decodare (PNG fără IDAT, JPEG fără SOS/date de scanare, fișier trunchiat, CRC greșit, bombă de decompresie) → 415 „Image is damaged or cannot be decoded”, fără rând, fără audit și fără fișier permanent. Memoria la decodare este mărginită de `DOCUMENT_MAX_IMAGE_PIXELS` (implicit 50 MP ≈ 150–200 MB RGB/RGBA); limita internă Pillow (~89 MP) rămâne activă.
- PDF: `%PDF-` la început și `%%EOF` în ultimii 2 KiB.
- Respinse cu 415: SVG, HTML, GIF, DICOM și orice alt tip; PNG/PDF trunchiate; JPEG fără dimensiuni; PDF care conține `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile(s)`, `/RichMedia`, `/XFA`, `/SubmitForm`, `/ImportData`, `/GoToE` (inclusiv cu escape `#xx`). Este o **euristică**; obiectele comprimate pot ascunde conținut. **Nu există scanare antivirus.**
- `photo` și `radiograph` acceptă numai JPEG/PNG (422).
- Peste limită: 413 (inclusiv fără `Content-Length`, prin flux chunked). Fișier gol: 422.

## Identitatea pacientului vizitei

Un document atașat unei vizite (activ **sau arhivat**) blochează schimbarea pacientului acelei programări: `PATCH /api/appointments/{id}` cu alt `patient_id` → 409 „Cannot change patient after clinical data has been recorded for this appointment”, ca pentru note și manopere. Celelalte câmpuri ale programării, rolurile și regulile de închidere/timer nu se schimbă.

Uploadul și reasignarea folosesc același lock pe rândul programării (reasignarea îl ia la începutul PATCH, uploadul la verificarea definitivă), deci sunt serializate:
- upload primul → commit document → reasignarea vede documentul → 409;
- reasignare prima → commit pacient nou → uploadul pe pacientul vechi citește rândul actualizat → 422, staging-ul este șters, fără rând/audit.

## Stocare

- Rădăcina trebuie să fie cale absolută, în afara repository-ului (inclusiv `frontend/public`); altfel 503. Nu există mount static.
- Încărcarea se scrie întâi în `<root>/.incoming/<random>.part` (0600, `O_EXCL`, `fsync`), apoi este legată la `<root>/<clinic_id>/<key[:2]>/<key>` cu `os.link`, unde `key` = 32 hex aleatori generați de server. Numele primit nu devine niciodată cale. `os.link` refuză o cheie existentă: un fișier clinic nu este suprascris tăcut.
- Ordinea: pre-verificare → staging → inspecție/decodare → verificare definitivă sub lock → rând DB (flush) → plasare fișier → commit. Orice eșec înainte de commit face rollback și șterge fișierul plasat și staging-ul: nu rămâne document vizibil fără fișier și nici fișier pentru o salvare eșuată. Un crash al procesului între plasare și commit poate lăsa un fișier fără rând (nevizibil); backupul îl raportează ca `orphan_files`.
- Lipsa fișierului pentru un rând existent → 404 „Document content unavailable”, fără căi interne.

## Date și audit

Tabel `clinical_documents` (migrare aditivă `t11_add_clinical_documents`, părinte `t08_add_treatment_plans`): pacient, vizită opțională (FK), dinte opțional (CHECK FDI în PostgreSQL), categorie, descriere, nume original (afișare sigură: ultima componentă, NFC, fără caractere de control/bidi, ≤200), tip, dimensiune, SHA-256, lățime/înălțime, cheie de stocare unică, **`clinical_date` (introdusă de utilizator, opțională) distinctă de `uploaded_at` (momentul înregistrării, server)**, autor, `Idempotency-Key`, status `active|archived` cu `archived_at/by/reason` (CHECK de coerență). Auditul folosește `audit_events` (`uploaded`, `viewed`, `downloaded`, `archived`), fără conținut binar sau nume de fișier. Nu se creează manopere, tarife, plăți sau segmente de timer. Ștergerea fizică nu este implementată.

## UI

Panoul „Documente și imagini” din dosarul pacientului (sub planurile de tratament, fără a duplica odontograma): regulile de format/limite, formular (fișier, categorie, vizită, dinte, dată clinică, descriere), filtre categorie/vizită/dinte, arhivate la cerere, vizualizator cu zoom (−/+/100%/Potrivește, derulare pentru deplasare) și comparație a două imagini cu zoom sincronizat sau independent. Salvarea este blocată cât timp cererea e în curs; eroarea păstrează fișierul și câmpurile, iar retry-ul folosește același `Idempotency-Key`. Panoul este montat cu cheie per pacient; un răspuns întârziat pentru pacientul anterior este ignorat.

## Erori

| Cod | Situație |
| --- | --- |
| 401 / 403 | neautentificat / rol fără acces T11 |
| 404 | pacient/document din altă clinică sau inexistent; conținut lipsă pe disc |
| 409 | `Idempotency-Key` refolosit cu alt conținut; document deja arhivat; coliziune la salvare (retry) |
| 413 | fișier peste limită; dimensiuni imagine peste limită |
| 415 | tip neacceptat, extensie nepotrivită, PDF activ, fișier trunchiat |
| 422 | vizită a altui pacient, FDI invalid, dată clinică în viitor, categorie imagine cu PDF, fișier gol, motiv gol |
| 503 | stocare neconfigurată/în repository/neinscriptibilă sau eșec de scriere |

## Backup

`scripts/pilot/backup.sh` creează un director cu SQLite + `documents/` + `MANIFEST.json`; `restore.sh` restaurează într-o copie izolată și verifică manifestul și SHA-256 pentru fiecare document. Vezi `docs/pilot/README.md`.
